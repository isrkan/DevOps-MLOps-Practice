## 4.6 — Application Modernization

### Infrastructure vs Application Modernization — A Quick Recap
Moving to the cloud can target two different layers.

- **Infrastructure modernization** changes *where* and *on what* our applications run — physical servers become cloud VMs, self-managed databases become managed cloud databases, the data center disappears.
- **Application modernization** changes *how the application itself is built* — large, single-piece codebases become small, independent services; deployments go from quarterly releases to multiple times per day; the app is redesigned to take advantage of cloud-native capabilities like autoscaling, managed services, and global distribution.

We can do infrastructure modernization without ever touching the application code (that is exactly what "rehosting" means). We can also do application modernization on infrastructure we already own. But the largest business gains come when both happen together.

> **Key Point:** Infrastructure modernization is about the *platform*. Application modernization is about the *software running on the platform*. The exam will test whether we can identify which one a scenario describes.

---

### The Benefits of Modern Cloud Application Development
A "modern cloud application" is an application built to take full advantage of the cloud — not one that just happens to be running on a cloud VM. The defining characteristics are: small, independent services; containerized deployment; automated build and release; designed to fail gracefully; scaled automatically by the platform.

These properties translate directly into business benefits:

**Faster time to market**
Small teams can build, test, and deploy small services independently. A feature that would have required coordinating across the entire engineering organization in a monolithic application can now be shipped by a single team in a single afternoon. For organizations whose competitors are releasing features weekly, this is the difference between leading the market and chasing it.

**Continuous improvement instead of "big bang" releases**
Modern applications are deployed continuously — sometimes dozens of times per day — through automated CI/CD pipelines. Each change is small, low-risk, and easy to roll back. There are no more multi-month release cycles, no more all-hands-on-deck launch weekends, no more "freeze" periods when nothing can change.

**Elastic scalability**
A modern cloud application scales each service independently and automatically. When the checkout service is under heavy load during a sale, only the checkout service scales up — not the whole application. When traffic drops back to normal, capacity shrinks back, and the bill shrinks with it. We never pay for capacity we are not actively using.

**Built-in resilience**
Modern applications assume that any individual component can fail at any time and design for automatic recovery. If a single container crashes, the orchestration platform (like Kubernetes) starts a new one within seconds. If an entire zone goes offline, traffic is routed to a healthy zone. Outages that would have brought a legacy application down for hours are absorbed without users noticing.

**Lower total cost of ownership**
Modern cloud applications use managed services for databases, messaging, monitoring, and identity — meaning engineering teams spend their time on the application logic that differentiates the business, not on the undifferentiated heavy lifting of running infrastructure.

**Easier to attract and retain talent**
Engineers want to work on modern stacks. Building careers on legacy monoliths is increasingly unattractive. Organizations running modern cloud applications have a meaningful advantage in hiring.

> **Key Point:** "Cloud-first" means new applications are built in the cloud by default. "Cloud-native" means the application is *architecturally designed* for the cloud — containers, microservices, autoscaling, managed services. A cloud-first application is not automatically cloud-native.

#### Cloud-First vs Cloud-Native at a Glance

| Term | What It Means | Example |
|------|---------------|---------|
| **Cloud-first** | When a new project starts, the cloud is the default choice — but the architecture may still resemble traditional applications | A company decides every new app must run on Google Cloud, but the first such app is a monolithic Java application running on a single VM |
| **Cloud-native** | The application is built around cloud-native patterns: containers, microservices, managed services, autoscaling, statelessness | An e-commerce app composed of 30 containerized microservices on GKE, using Cloud SQL, Pub/Sub, and Cloud Storage |

### The Application Modernization Journey
Application modernization is not a single project — it is a multi-year journey, and most organizations move through identifiable stages:

1. **Starting point: legacy on-premises monolith** — a single, large application running on physical hardware in a data center, deployed every few months, scaled by buying bigger servers
2. **Rehost in the cloud** — move the application as-is to cloud VMs; immediate operational gains, no application changes
3. **Replatform / move and improve** — adopt managed services (managed database, managed message queue) while keeping the application largely intact
4. **Refactor toward cloud-native** — break the monolith into microservices, containerize them, deploy through automated pipelines
5. **End goal: cloud-native** — fully containerized, microservice-based, continuously deployed, autoscaling, observable, resilient

Most organizations are working at multiple stages simultaneously across their portfolio — some applications are still being rehosted while others are already fully cloud-native.

### Rehosting Legacy Applications in the Cloud
**Rehosting** — also called **"lift and shift"** — is the migration strategy of moving an application from on-premises to the cloud with **no changes** to its code or architecture. The application runs on a cloud virtual machine that looks, from the application's perspective, almost identical to the physical server it used to run on.

Rehosting is the simplest and fastest path to the cloud, and for many legacy applications it is the **only realistic path**.

#### Why Rehost Legacy Applications?
Many enterprises have applications that have been running for 10, 15, or 20 years and that the business still depends on every day — ERP systems, financial back-office software, manufacturing control systems, custom internal applications written by people who no longer work at the company. Rewriting these applications is often not feasible:

- The original developers have left and no one fully understands the code
- The application is built on a framework or language that has fallen out of common use
- The cost of rewriting would run into millions of dollars with multi-year timelines
- The application "works" — the business case for a complete rewrite is weak

For these applications, rehosting offers most of the cloud's operational benefits without any of the rewrite risk.

#### The Advantages of Rehosting (Even Without Code Changes)

| Benefit | Why It Matters |
|---------|----------------|
| **Exit the data center** | No more hardware refresh cycles, no more leases, no more on-site staff for physical infrastructure |
| **Pay only for what you use** | Stop and start VMs on demand; right-size them to actual usage instead of peak |
| **Improved reliability** | Cloud infrastructure is built with redundancy at every layer; even unmodified legacy apps benefit |
| **Faster disaster recovery** | Cloud snapshots and multi-region replication are dramatically easier than on-premises DR |
| **Global reach** | Run the application closer to users in any of Google's 40+ regions, with no hardware procurement |
| **Easier security patching** | Centralized image management, automated OS patching, integrated identity |
| **Pathway to further modernization** | Once the app is in the cloud, the team can incrementally adopt managed services (replatform) and eventually refactor — without a "big bang" change |

#### The  Drawbacks of a Rehost Migration Path
While rehosting provides a rapid exit from physical data centers, it introduces specific long-term drawbacks and limitations that organizations must navigate:
* **Compounded Complexity:** Moving a legacy application as-is means transferring all of its existing technical debt, unpatched vulnerabilities, configuration quirks, and undocumented dependencies straight into the cloud. Managing these outdated configurations in a cloud environment can increase operational complexity for infrastructure teams.
* **Elevated Migration Risk:** Because legacy applications often rely on static IP addresses, low-latency local network broadcasts, or specific hardware attachments on-premises, moving them to a virtualized cloud network can cause unexpected failures. Without code modifications, troubleshooting these architectural mismatches mid-migration introduces severe downtime risks.
* **Vendor Lock-In:** Rehosting an application on cloud-provider-specific VM configurations, or relying on proprietary migration tooling to keep the system operational, binds the application tightly to that specific cloud vendor’s platform. Extracting a monolithic application later or migrating it to another cloud provider becomes exceptionally difficult and costly.
* **Missed Cloud Optimization:** The application remains architecturally rigid. It cannot automatically scale horizontally, its release cadence remains slow, and it does not inherently benefit from application-layer resilience.

> **Key Point:** Rehosting is about *infrastructure* change, not *application* change. The exam will sometimes describe a scenario where a company moves an SAP system or Oracle database to Compute Engine "with no changes" — this is rehosting, every time.

#### Google Cloud Products That Support Rehosting

| Product | Role in Rehosting |
|---------|-------------------|
| **Compute Engine** | The destination — VMs that run the legacy application the same way the on-premises servers did |
| **Migrate to Virtual Machines** (part of Google Cloud Migration Center) | Tooling that copies on-premises VMs (VMware, Hyper-V, physical servers) into Compute Engine, often with minimal downtime |
| **Cloud Storage** | Hosts the disk images and backups during and after migration |
| **Cloud VPN / Cloud Interconnect** | Provides the secure network link between on-premises and Google Cloud during the transition |

**Business example:** A regional insurance company runs its policy administration system on aging Windows Server hardware in two leased data centers. A full rewrite would take 3+ years. Instead, the team uses Migrate to Virtual Machines to copy 60 servers into Compute Engine over a weekend. The application behaves exactly the same way it did before — but the data center leases can now be terminated, hardware refresh cycles end, and disaster recovery improves dramatically. Over the next two years, individual services are gradually replatformed (managed SQL Server, Cloud Load Balancing) and eventually a few are refactored into microservices on GKE.

### How Application Modernization and Rehosting Fit Together
Rehosting is often misunderstood as "the lazy option" — but in practice, it is a deliberate first step in a longer modernization plan. A well-run modernization program typically looks like this:

1. **Rehost** as much of the legacy estate as possible, as quickly as possible — get out of the data center and start saving money
2. **Replatform** the components that benefit most from managed services (databases, message queues, identity)
3. **Refactor** the highest-value applications — the ones whose performance, scalability, or release velocity is limiting the business — into cloud-native designs
4. **Reimagine** only the few applications where the existing design fundamentally cannot meet future requirements

This portfolio approach gives the business immediate wins (cost, reliability) while focusing scarce engineering effort on the modernization investments with the strongest return.

> **Key Point:** A scenario that says "the company wants to move quickly and minimize risk" almost always points to **rehosting**. A scenario that says "the company wants to take full advantage of cloud-native features like autoscaling and microservices" points to **refactoring** or building new cloud-native applications.
