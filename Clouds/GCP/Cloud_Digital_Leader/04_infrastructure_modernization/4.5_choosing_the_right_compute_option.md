## 4.5 — Choosing the Right Compute Option

### When to Use Each Product

| Product | Type | What You Manage | What Google Manages | Best For |
|---------|------|-----------------|---------------------|----------|
| **Compute Engine** | IaaS (VMs) | OS, software, scaling, patches | Physical hardware, virtualization | Legacy app migration, specialized software, full OS control |
| **Google Kubernetes Engine (GKE)** | Managed containers | Application containers, deployment config | Kubernetes control plane, node patches | Complex microservices, large container fleets |
| **App Engine** | PaaS | Application code only | Runtime, OS, scaling, infrastructure | Web apps and APIs; developers want to focus only on code |
| **Cloud Run** | Managed serverless containers | Container image | Everything else | Stateless APIs, microservices, variable traffic patterns |
| **Cloud Functions** | Serverless functions | Single function code | Everything else | Simple event-triggered tasks, lightweight integrations |

> **Key Point:** The exam frequently asks which compute product is "most managed" (Cloud Functions / Cloud Run — zero infrastructure) vs "most control" (Compute Engine — full VM). Know the trade-off: more management by Google = less flexibility for us, but less operational work.

### The Control vs. Responsibility Spectrum
A useful mental model: every step you move toward serverless, you trade control for convenience. This is not a quality ranking — the right product depends entirely on the workload.

```
Most Control / Most Responsibility          Least Control / Least Responsibility
        │                                                       │
        ▼                                                       ▼
  Compute Engine ──── GKE ──── App Engine ──── Cloud Run ──── Cloud Functions
  (you manage         (you      (you manage      (you manage    (you manage
   everything         manage    code only)        container      one function)
   above hardware)    containers)                  image only)
```

As you move right:
- Less infrastructure to configure and maintain
- Faster to deploy and iterate
- Less flexibility over the underlying environment
- Billing becomes more granular (per request / per millisecond)
- Cold starts become a consideration (serverless products may have a small latency spike after a period of inactivity)

### Side-by-Side: Serverless Products
Cloud Run, App Engine, and Cloud Functions are often confused because all three are "serverless." The distinction is granularity.

| | Cloud Functions | App Engine | Cloud Run |
|---|---|---|---|
| **Unit of deployment** | One function | Full application | One container image |
| **Trigger** | Event-driven (file upload, Pub/Sub message, HTTP) | HTTP requests | HTTP requests / events |
| **Runtime support** | Fixed runtimes (Node.js, Python, Go, Java…) | Fixed runtimes (Standard) or custom (Flexible) | Any language, any framework |
| **Max execution time** | 60 min (2nd gen) | Depends on instance class | 60 min (default), up to 24h |
| **Scales to zero** | Yes | Yes (Standard) | Yes |
| **Best for** | Automation, lightweight integrations | Web apps and APIs | Portable services, microservices |

### Side-by-Side: Container Products
GKE and Cloud Run both run containers, but they target very different levels of complexity.

| | Cloud Run | GKE |
|---|---|---|
| **Who manages Kubernetes?** | Google (fully abstracted away) | Google manages control plane; you manage workloads |
| **Networking between services** | Limited; best for independent services | Full service mesh; services communicate freely |
| **Scaling** | Fully automatic, including to zero | Autoscaling configured per workload |
| **Learning curve** | Low — deploy a container, done | High — requires Kubernetes knowledge |
| **Best for** | Single containerized service, APIs | Many microservices with dependencies between them |
