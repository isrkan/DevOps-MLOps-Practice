## 4.1 — Cloud Modernization and Migration

### Why Modernization Matters
Organizations modernize infrastructure and applications for clear business reasons:

- **Cost reduction** — data center leases, hardware refresh cycles (every 3–5 years), power, cooling, and staff managing physical servers are expensive. Cloud eliminates most of these costs.
- **Speed** — launching a new product or service requires provisioning new servers, which can take weeks or months on-premises. In the cloud, it takes minutes.
- **Resilience** — on-premises infrastructure has single points of failure. Cloud infrastructure is built with redundancy at every layer.
- **Innovation** — access to AI, ML, analytics, and modern developer tools is instant on the cloud; building equivalent capabilities on-premises is prohibitively expensive.
- **Talent** — engineers want to work with modern tools. Legacy infrastructure makes it harder to attract and retain skilled people.

**Infrastructure modernization** means replacing or upgrading the underlying servers, networking, and storage that our applications run on — moving from physical hardware to cloud-managed infrastructure.

**Application modernization** means changing how the applications themselves are built and deployed — from large, monolithic codebases to smaller, independent services that can be updated without touching the rest of the system.

### The Migration Strategy Spectrum — The 7 R's
Not every application migrates the same way. Organizations assess each workload individually and choose the most appropriate strategy. Think of this like moving to a new house: some furniture you bring as-is, some you sell, some you replace entirely.

**What is a Workload?**
A **workload** is a specific application, service, or capability that can be run in the cloud or on-premises. Workloads are the fundamental building blocks of an enterprise IT portfolio and include containers, databases, and virtual machines. Every migration plan starts by mapping out and evaluating these individual workloads.

> **Key Point:** The exam regularly tests our ability to match a scenario to the correct migration term. Memorize all seven.

| Strategy | Plain-English Definition | Analogy | When to Use |
|----------|--------------------------|---------|-------------|
| **Retire** | Shut down the application permanently — it's no longer needed | Throwing away old furniture we never use | Duplicate systems, unused applications, apps replaced by SaaS alternatives |
| **Retain** | Keep the application exactly where it is — do not migrate it | Keeping a fragile antique that can't survive a move | Regulatory restrictions, unsupported hardware dependencies, very high migration risk with low ROI |
| **Rehost** *(Lift and Shift)* | Move the application to a cloud virtual machine with **zero changes** to the code or architecture | Moving all our furniture exactly as-is to the new house | Fast migration with immediate cost savings; works for most legacy apps; does not optimize for cloud but gets us off old hardware quickly |
| **Replatform** *(Move and Improve)* | Move to the cloud and make **minor optimizations** without rewriting the application — for example, switching from a self-managed database to a managed cloud database | Moving our furniture but replacing the old bookshelves with better-fitting ones for the new space | Moderate effort; gains operational benefits like automatic backups, managed upgrades, and better reliability without a full rewrite |
| **Refactor** *(Re-architect)* | Significantly **rewrite portions** of the application to take advantage of cloud-native capabilities — microservices, containers, managed services | Renovating the house completely: new walls, new layout, modernized throughout | High effort and cost, but maximum cloud benefit; best for applications where performance or scalability limitations are hurting the business |
| **Reimagine** | **Rebuild from scratch** using cloud-native principles — the old application is completely replaced | Tearing down the old house and building a new one on the same lot | Applications where the original design fundamentally cannot meet business needs; high investment, highest long-term value |
| **Repurchase** | Replace the application with a **commercial SaaS product** — stop maintaining it yourself | Moving out and checking into a hotel instead of owning a home | Legacy HR, CRM, or ERP systems that can be replaced by Salesforce, Workday, or Google Workspace |

> **Key Point:** A real migration project uses a *portfolio approach* — no single strategy applies to all workloads. A typical enterprise might retire 15%, retain 10%, rehost 40%, replatform 20%, and refactor 15%.

**Key terms to know:**
- **Workload** — any application, service, database, or computing job that runs on infrastructure. Every migration plan starts by inventorying workloads.
- **Technical debt** — the accumulated cost of shortcuts and outdated decisions in technology; the older an application, the more technical debt it tends to carry.
